# Software Architecture Document

**Product:** BeautyBook - Online Salon Marketplace
**Version:** 1.0 - Initial architecture baseline
**Date:** 2026-11-18
**Status:** Active baseline. ADR-0005 and ADR-0010 were accepted on 2026-11-18. Any remaining
"Proposed" ADR must be finalized before the affected feature is implemented.

---

## 1. Purpose and scope

This document describes how BeautyBook is structured: its architectural style, modules, domain
model, persistence strategy, booking consistency model, API and frontend design, security
baseline, and deployment expectations.

It is a **design baseline**, not permission to implement. Implementation follows the feature
intake gate in `AGENTS.md` and `Task-List.md`.

The first release is a single deployable product serving multiple independent salons. It
deliberately starts as a modular monolith.

---

## 2. Architecture drivers

1. Prevent overlapping active bookings for the same salon.
2. Keep appointment times and working hours correct across timezones and daylight-saving changes.
3. Enforce strict separation between customers, salon owners, and administrators.
4. Support a professional public salon page with services, prices, hours, and images.
5. Make the booking flow trustworthy: revalidation, idempotency, and a clear conflict response.
6. Keep local development and testing practical without hiding PostgreSQL-specific behavior.
7. Allow later additions (reviews, payments, staff, notifications) without rewriting the core.
8. Protect personal data and uploaded images.
9. Keep the codebase understandable for a learning developer.

## 4. Architectural style

### 4.1 Modular monolith

One FastAPI application and one primary PostgreSQL database, divided internally into domain
modules. This provides:

- simple deployment and debugging,
- strong transactional consistency for booking,
- clear module boundaries that can be extracted later if justified,
- a smaller operational burden than microservices.

Microservices, event sourcing, CQRS, and distributed locks are explicitly out of scope for the
first release.

### 4.2 Backend layers inside each module

Use a consistent, simple internal structure:

```text
backend/app/modules/<module>/
  domain.py       # Framework-free business rules, value objects, policies
  models.py       # SQLAlchemy 2.x mappings
  schemas.py      # Pydantic request/response schemas
  repository.py   # Persistence queries
  service.py      # Use cases, authorization, transaction boundaries
  router.py       # HTTP endpoints only
```

Dependency direction:

```text
HTTP request
   |
   v
router.py  (parse, authenticate, map status codes)
   |
   v
service.py (authorize, orchestrate, own transaction)
   |              \
   v               v
repository.py     domain.py
   |
   v
PostgreSQL
```

Rules:

- `domain.py` imports no FastAPI, SQLAlchemy, or HTTP code.
- Routers contain no business rules.
- Services own transactions and authorization.
- Repositories contain queries, not policy decisions.
- Modules do not import another module's ORM models. They reference IDs and call the owning
  module's public service/query interface.
- Module dependencies must be acyclic.
- A cross-module read model is allowed only when documented in the feature spec.

### 4.3 Shared code

Shared code lives in `backend/app/core/` and `backend/app/infrastructure/`:

- `core/`: configuration, security primitives, error types, logging, request IDs, pagination
  helpers.
- `infrastructure/`: database session/engine, email adapter, image storage adapter, password
  hashing, clock abstraction when needed.

Shared code must be genuinely cross-cutting. Do not create a `utils/` dumping ground.

### Module dependency direction

```text
identity ---> users
    |
    +-----------------------+
    |                       |
    v                       v
salons ----------------> services
    |                       |
    +--------+--------------+
             |
             v
        availability
             |
             v

             |
             v

```

## 8. Domain model overview

The final schema is refined in feature specs and migrations. The baseline entities are:

### Identity and users

- **User:** id, normalized email, password hash, full name, phone (optional), account status
  (`pending_approval`, `active`, `rejected`, `suspended`), preferred timezone, locale, timestamps.
- **UserRole:** user id, role (`customer`, `salon_owner`, `admin`). Unique per user/role. The data
  model supports multiple roles even if the MVP UI exposes one primary role.
- **Session:** id, user id, hashed token, expiry, revocation, created timestamp. Used if
  DB-backed cookie sessions are accepted.
- **OwnerApplication:** id, user id (one per user in the MVP), salon name, city, phone, IANA
  timezone, ISO 4217 currency, optional description, status (`pending`, `approved`, `rejected`),
  rejection reason, reviewed by, reviewed at, submitted at. This records the approval gate; it is
  not the full salon profile, which arrives in F-004.
- **EmailVerificationToken / PasswordResetToken:** user id, token hash, expiry, used timestamp.

### Salon and media

- **Salon:** id, owner user id (unique in MVP), name, unique slug, description, address fields
  (`line1`, `line2`, `city`, `postal_code`, `country_code`), phone, public email, IANA timezone,
  ISO 4217 currency, status (`draft`, `pending_review`, `published`, `suspended`), timestamps.- **SalonPhoto:** id, salon id, storage key, content type, width, height, byte size, alt text,
  sort order, cover flag, created timestamp.

### Services

- **Service:** id, salon id, name, description, duration minutes, price minor units, optional
  pre/post buffer minutes, category/tag, active flag, archived timestamp, timestamps.
  Currency is inherited from the salon in the MVP and snapshotted on bookings.

### Availability

- **WorkingHours:** id, salon id, weekday (`0` Monday to `6` Sunday), local open time, local close
  time. Multiple non-overlapping intervals per weekday are allowed.
- **TimeOff:** id, salon id, start instant (UTC), end instant (UTC), reason, created by, created
  timestamp. Used for holidays and other unavailable periods.

### Booking

- **Booking:** id, salon id, service id, customer user id, `start_at` (UTC), `end_at` (UTC),
  `blocked_from` (UTC), `blocked_until` (UTC), status, snapshots (service name, duration, price,
  currency, salon timezone, cancellation policy version), customer note, idempotency key,
  cancellation metadata, timestamps.
- **BookingEvent:** id, booking id, event type, actor user id (nullable for system events),
  metadata, created timestamp. Append-only.

### Notifications and audit

- **OutboxMessage:** id, message type, payload, status, attempts, available at, processed at,
  last error, created timestamp.
- **AuditLog:** id, actor user id, action, target type, target id, reason, redacted metadata,
  request id, created timestamp.
- **PlatformSetting:** key, value, updated by, updated timestamp.

### Future entities (do not create yet)

- **Review:** only when F-015 is Ready.
- **Payment / Refund:** only when F-016 is Ready.
- **StaffMember / Resource:** only when multi-capacity is approved.

## 9. Identity and authorization

### 9.1 Authentication

The browser-first strategy is:

- Argon2id password hashing.
- Short-lived, DB-backed session identifier in a secure, `HttpOnly`, `SameSite=Lax` cookie.
- CSRF token for state-changing requests.
- Session revocation on logout and password change.
- Email verification before sensitive actions.
- Rate limiting on registration, login, and password reset.
- Short-lived, single-use reset tokens stored as hashes.

This decision is recorded as **accepted** in ADR-0005 (2026-11-18) and is implemented by F-001.

### 9.2 Authorization

Use role checks plus resource ownership:

| Actor | Allowed |
|---|---|
| Public visitor | Read published salons, active services, portfolio images, public availability. |
| Customer | Manage own profile and own bookings. |
| Salon owner | Manage own salon, services, images, working hours, time off, and that salon's bookings. |
| Administrator | Perform explicitly permitted platform operations, with audit. |

A role alone is not enough. For example, `GET /owner/salon` must resolve the salon from the
authenticated owner, not from a client-supplied owner id. Every protected endpoint needs a
negative authorization test.

BeautyBook has **three separate trust paths**, not a role selector:

- **Customer:** `/register` creates an active customer with a session.
- **Salon owner:** `/register/owner` creates a pending account and a pending application. The
  `salon_owner` role is granted only when an administrator approves the application. A pending
  owner has no session and no owner role.
- **Administrator:** never available through public registration. The first administrator is
  created by a local CLI command; later administrators are granted by an existing administrator
  through an administrator-only endpoint.

No client can choose its own role or status. See ADR-0010.

## 10. Salon and media design

### 10.1 Public profile

The public profile is a read model composed from:

- salon fields (name, description, address, contact, timezone, currency),
- cover photo and gallery,
- active services with price and duration,
- weekly working hours,
- advertised availability for a requested date range.

Only published, non-suspended salons are exposed. Draft profiles are visible only to the owner and
administrators.

### 10.2 Images

- Upload endpoint accepts multipart form data.
- Validate size, declared type, and actual bytes.
- Decode with an image library, re-encode if needed, and strip EXIF/location metadata.
- Generate a random storage key; never use the original filename as the key.
- Store metadata in `salon_photos` and the bytes in a storage adapter.
- Serve through a controlled endpoint or object-storage origin with long-lived cache headers.
- Enforce a per-salon image limit and one cover image.
- Deleting an image marks it deleted and removes it from public output; a cleanup job may remove
  the stored object later.

The production storage provider is decided in ADR-0006.

## 11. Time, availability, and booking design

### 11.1 Time model

- Appointment instants: UTC (`timestamptz` in PostgreSQL).
- Salon working hours: local wall-clock times plus the salon's IANA timezone.
- Customer display timezone: the customer's preference or browser timezone.
- API responses include UTC instants, the salon timezone, and display-ready local values.

### 11.2 Working hours

`working_hours` stores weekday + local open/close times. Multiple rows per weekday allow split
shifts. Rules:

- `0 <= weekday <= 6`.
- `open_time < close_time` for same-day intervals.
- Intervals for the same salon and weekday must not overlap.
- Overnight hours (crossing midnight) are out of scope until the product decision changes.

### 11.3 Availability algorithm

Inputs:

- salon id, service id, date range, requested display timezone,
- service duration and buffers,
- weekly working hours,
- time off,
- existing blocking bookings,
- slot interval, minimum notice, booking horizon,
- current time.

Steps:

1. Resolve the salon timezone and validate that the salon is published.
2. Load the active service and its duration/buffers.
3. For each local date in the range, expand working-hour intervals into local candidate starts at
   the configured slot step.
4. Convert each candidate local start to UTC using the salon timezone.
5. Reject nonexistent local times and apply the documented ambiguous-time convention.
6. Reject candidates that violate minimum notice or booking horizon.
7. Reject candidates whose occupied interval overlaps time off.
8. Reject candidates whose occupied interval overlaps active bookings.
9. Ensure the occupied interval fits inside a working interval (buffers included).
10. Return the remaining candidates, ordered by start time, with UTC and local display fields.

The calculation is a read model. It is **advisory** and may be stale by the time the customer
submits.

### 11.4 DST policy

- Nonexistent local times (spring-forward gap) are skipped.
- Ambiguous local times (fall-back overlap) use the first occurrence (`fold=0`) until a different
  policy is approved.
- Schedule generation and booking validation use the same conversion function.
- Tests cover a spring-forward date and a fall-back date in a timezone such as `Europe/Berlin` or
  `America/New_York`.

### 11.5 Booking transaction

The booking use case executes in one database transaction:

1. Authenticate the customer and validate the request schema.
2. Load the salon and service; verify the salon is published and the service is active.
3. Load the salon timezone, slot policy, and cancellation policy.
4. Validate the requested start is aligned to the slot grid.
5. Compute `start_at`, `end_at`, `blocked_from`, and `blocked_until` in UTC.
6. Validate working hours, time off, minimum notice, booking horizon, and duration fit.
7. Insert the booking with a blocking status and its snapshots.
8. Let the database reject an overlap (exclusion constraint) if another transaction won the race.
9. Insert a `booking_event` and an outbox message in the same transaction.
10. Commit.
11. Return the booking. Notification delivery happens after commit.

No email, storage, or payment network call occurs inside this transaction.

### 11.6 Double-booking prevention

The authoritative mechanism is a PostgreSQL exclusion constraint over the salon and the occupied
interval:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
ADD CONSTRAINT bookings_no_overlap
EXCLUDE USING gist (
  salon_id WITH =,
  tstzrange(blocked_from, blocked_until, '[)') WITH &&
)
WHERE (status IN ('pending_confirmation', 'confirmed'));
```

Notes:

- `[)` is the half-open interval convention: touching endpoints do not conflict.
- Buffers are already included in `blocked_from`/`blocked_until`.
- The partial predicate restricts the constraint to slot-blocking states.
- The exact enum/status representation and predicate must be finalized in F-009.
- An application-level "SELECT then INSERT" is not sufficient, even if it is also performed.
- The constraint violation must be translated into a stable `409 SLOT_UNAVAILABLE` response.
- SQLite cannot validate this behavior. Concurrency tests run on PostgreSQL.

This decision is recorded as proposed in ADR-0003 and must be finalized before F-009.

### 11.7 Idempotency

- The client sends an `Idempotency-Key` header for booking creation.
- Uniqueness is scoped to the customer: `UNIQUE (customer_user_id, idempotency_key)`.
- Same key + same request fingerprint: return the original booking (`200` or `201` as defined).
- Same key + different request: return `409 IDEMPOTENCY_KEY_REUSED`.
- The key must be stored in the same transaction as the booking.

### 11.8 Booking lifecycle

Initial states:

- `PENDING_CONFIRMATION` - owner approval required; blocks the interval until expiry.
- `CONFIRMED` - accepted and reserved.
- `CANCELLED_BY_CUSTOMER`
- `CANCELLED_BY_SALON`
- `COMPLETED`
- `NO_SHOW`
- `EXPIRED` - a pending request expired.

Blocking states: `PENDING_CONFIRMATION`, `CONFIRMED`.

Example transitions:

```text
PENDING_CONFIRMATION -> CONFIRMED | REJECTED | EXPIRED
CONFIRMED            -> CANCELLED_BY_CUSTOMER | CANCELLED_BY_SALON | COMPLETED | NO_SHOW
```

A transition must be validated by domain policy, recorded in `booking_events`, and authorized
against the actor. Terminal states cannot transition back to active states in the MVP.

Instant booking is the simplest MVP mode: create `CONFIRMED` directly. The schema supports the
pending state so approval mode can be enabled without a redesign, if the product decision chooses
it.

## 12. Database strategy

### 12.1 PostgreSQL

- Default database for local development, integration tests, and production.
- Provides the authoritative concurrency, transaction, and exclusion-constraint behavior.
- Use `timestamptz` for instants.
- Use `numeric` only for non-money decimal values; money uses integer minor units.
- Use check constraints for durations, prices, statuses, weekdays, and interval ordering.
- Use partial unique indexes where invariants require them (for example, one cover photo per
  salon).
- Define indexes for public search and booking lookups.

### 12.2 SQLite

- Allowed only for fast, portable unit-level tests.
- Enable foreign keys on every connection.
- Do not use SQLite-specific SQL in application logic.
- Do not use SQLite to claim concurrency correctness.
- Never use SQLite in production.

### 12.3 Migrations

- Alembic manages all schema changes.
- Never use `create_all()` as the production migration strategy.
- Never edit a released migration; add a new one.
- Test upgrade from a clean database and from the previous supported schema.
- Document PostgreSQL-specific steps (extensions, exclusion constraints) in the migration.
- Provide rollback notes; not every data migration is perfectly reversible, and that must be
  stated honestly.

### 12.4 Deletion and retention

- Users, salons, and services referenced by bookings are deactivated/archived, not deleted.
- Bookings and booking events are retained for operational and audit purposes.
- Image metadata may be soft-deleted; stored objects are cleaned up asynchronously.
- Retention periods are confirmed before production.

## 14. Frontend architecture

### 14.1 Organization

```text
frontend/src/
  app/                 # bootstrap, layouts, global providers
  router/              # routes and guards
  modules/
    auth/              # login, register, verify, reset
    salons/            # public discovery and salon profile
    services/          # service comparison
    booking/           # slot picker, checkout, confirmation
    customer-dashboard/
    owner-dashboard/
    admin/
  components/          # shared presentational components
  composables/         # reusable composition functions
  services/api/        # typed HTTP client and endpoint wrappers
  stores/              # Pinia: session, UI preferences
  assets/styles/       # tokens, reset, global styles
```

### 14.2 State

- Pinia holds shared client state: authenticated user summary, UI preferences, maybe a booking
  draft.
- Server data is fetched per screen through typed API wrappers and kept local unless sharing is
  genuinely needed.
- Do not build a global cache of all salons and bookings.
- Do not persist sensitive data in browser storage.

### 14.3 Styling

- CSS custom properties define color, spacing, radius, typography, and breakpoints.
- Mobile-first layout with CSS Grid and Flexbox.
- Scoped styles for components; global styles only for tokens/reset.
- No UI framework is required for the first release. This is recorded in ADR-0007.
- Accessibility and responsive behavior are acceptance criteria, not afterthoughts.

### 14.4 Authorization in the UI

Route guards improve user experience. They are **not** security. Every protected action is
authorized again by the backend.

## 15. Notifications and background work

- Use a transactional outbox: booking and outbox message are committed together.
- A worker claims available messages, sends email through an adapter, and records attempts.
- Retries use bounded backoff and deduplication.
- Notification failure never rolls back a booking.
- Email content is rendered from templates and contains only necessary data.
- Reminders are scheduled from confirmed bookings and deduplicated per booking/interval.
- The worker technology is selected when F-013 is specified; do not add a broker before then.

## 16. Security and privacy

Threat model at minimum:

- account takeover and brute force,
- privilege escalation and insecure direct object references,
- booking enumeration and personal-data exposure,
- CSRF/XSS and injection,
- malicious file upload and path traversal,
- secret leakage,
- webhook spoofing (future payments),
- denial of service on public availability and booking endpoints.

Controls:

- Argon2id password hashing and rate limiting.
- Secure cookie sessions with CSRF protection, or a documented token architecture.
- Server-side role and ownership checks on every protected operation.
- Input validation with Pydantic and database constraints.
- Parameterized queries through SQLAlchemy; no string-built SQL with user input.
- Upload validation by content and size; random storage keys; no executable content.
- Security headers and a restrictive content security policy where practical.
- Structured logs with request IDs and redaction.
- Audit records for privileged actions.
- Data minimization and retention/deletion procedures.
- TLS in transit and encrypted backups in production.

Do not claim legal compliance without a documented review.

## 17. Non-functional targets

Initial targets to validate with real measurements:

- Service availability: 99.5% monthly in the first production stage.
- p95 under 500 ms for ordinary API calls, excluding external providers.
- Availability queries measured separately with representative data.
- Zero accepted overlapping active bookings for a single-capacity salon.
- No known critical/high vulnerabilities at release.
- WCAG 2.2 AA target.
- RPO <= 24 hours and RTO <= 8 hours initially; tighten based on business need.
- Automated tests, migrations, linting, and type checks on every change.

These are engineering targets, not measured guarantees.

## 18. Deployment view

Initial deployment:

- Static frontend build served by a CDN or web server.
- FastAPI behind a reverse proxy/load balancer.
- PostgreSQL with managed backups.
- A background worker for outbox and reminders.
- Transactional email provider.
- S3-compatible object storage for images.
- Centralized logs and basic metrics.

Containerize for repeatable development and deployment. Use environment-specific configuration
and secrets; never commit production credentials. CI runs lint, type checks, tests, and migration
validation. Production migrations are reviewed and applied with a rollback plan.

Exact infrastructure choices belong in `infra/` and F-018.

## 19. Testing strategy

| Layer | Tool | Scope |
|---|---|---|
| Backend unit | pytest | Domain rules, availability math, pricing, state transitions, policies. |
| Backend integration | pytest + PostgreSQL | Repositories, transactions, constraints, API endpoints, migrations. |
| Backend concurrency | pytest + PostgreSQL | Simultaneous overlapping booking attempts. |
| Backend security | pytest | Auth boundaries, IDOR, upload validation, rate limits. |
| Frontend unit | Vitest + Vue Test Utils | Components, composables, form behavior. |
| Frontend E2E | Tool chosen in F-001 | Customer booking, owner management, admin moderation. |
| Contract | OpenAPI schema tests | Request/response compatibility. |

SQLite tests are useful but cannot validate PostgreSQL exclusion constraints or true concurrent
behavior.

## 20. Architecture risks

| Risk | Impact | Mitigation |
|---|---|---|
| Double booking under concurrency | Critical | PostgreSQL exclusion constraint, idempotency, concurrency tests |
| Timezone/DST errors | High | UTC + IANA model, shared conversion function, boundary tests |
| SQLite/PostgreSQL behavior mismatch | High | PostgreSQL integration suite, no production SQLite |
| Owner accesses another salon's data | Critical | Ownership checks and negative authorization tests |
| Customer accesses another booking | Critical | Object-level authorization tests |
| Malicious image upload | High | Content validation, size limits, random keys, safe serving |
| Notification failure after booking | Medium | Transactional outbox, retries, monitoring |
| Scope expansion | High | Feature gate, roadmap, non-goals |
| Money rounding errors | High | Integer minor units, explicit currency |
| Unclear cancellation policy | Medium | Resolve before F-012, snapshot policy version |

## 21. ADR governance

Create one ADR for each material decision. ADRs are historical records; supersede rather than
rewrite accepted decisions.

Current ADRs:

- `0001-modular-monolith.md` - modular monolith.
- `0002-database-strategy.md` - PostgreSQL main, SQLite for lightweight tests.
- `0003-booking-concurrency.md` - overlap prevention (proposed).
- `0004-timezone-model.md` - UTC instants and IANA timezones.
- `0005-authentication-session-strategy.md` - session strategy (accepted).
- `0006-image-storage.md` - image storage (proposed).
- `0007-frontend-styling.md` - plain CSS with design tokens.
- `0008-money-representation.md` - integer minor units and salon-level currency.
- `0009-authorization-model.md` - role plus resource-ownership checks.
- `0010-role-assignment.md` - two public registration flows with administrator approval; admin
  accounts are never public.

Future ADRs are required for:

- the notification worker/outbox implementation,
- payments and refunds,
- external calendar integration,
- multi-staff/resource capacity,
- any new major dependency or service.

## 22. Open decisions

The following decisions must be resolved in the relevant feature SPEC before implementation:

- guest booking vs mandatory account,
- salon self-publishing vs admin approval,
- instant confirmation vs owner approval,
- one salon per owner and one owner per salon,
- capacity one per salon vs staff/resources,
- launch countries, currencies, and languages,
- cancellation/reschedule/no-show policies,
- booking horizon, minimum notice, slot granularity, pending expiry,
- deposits/payments in the first release,
- production image storage provider,
- transactional email provider,
- review timing and moderation,
- city search vs geocoding/radius search,
- overnight working hours.

Do not encode an unanswered decision as an implicit assumption.
